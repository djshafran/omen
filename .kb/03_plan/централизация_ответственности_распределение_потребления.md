# Централизация управляющей логики в одном изолированном use-case модуле (без смены функциональности)

## Summary
На основе локального `omen` (graph/clones/complexity/search) и подхода `sourceatlas` (`overview` + `flow` + `pattern`) целевые места централизации уже определяются однозначно: оркестрация use-case сейчас размазана между CLI и MCP, при этом правила исполнения и маршрутизации частично дублируются.  
Цель: вынести только управляющую логику (routing + orchestration + policy), не трогая аналитику как domain-логику и не переопределяя поведение.
Дополнительное требование по semantic internals: AST-ветви внутри функций должны полноценно участвовать в индексировании, хранении и поисковой выдаче (как отдельные символы `branch`), без регрессий для текущего `function`-поиска.

## Целевой изолированный модуль
1. Ввести единый namespace-модуль `src/control/` как use-case orchestration слой.
2. Внутри `src/control/` держать только сценарии использования: `single_analysis`, `semantic_query`, `semantic_query_hyde`, `diff`, `batch_all`, `batch_report`.
3. Внутри `src/control/` иметь единственный `ToolCatalog` (source of truth) для:
`tool_name`, `cli_command_binding`, `requires_git`, `supports_scope`, `input_schema_for_mcp`, `executor`.
4. Внутри `src/control/` иметь единый `ContextFactory`:
`resolve_path_policy`, `discover_git_root`, `compute_git_scope`, `build_fileset`, `build_analysis_context`.
5. Адаптеры `main.rs` и `mcp/mod.rs` оставить тонкими: только transport-level parsing/formatting, без переопределения use-case логики.

## Public/API changes
1. Внешний CLI/MCP контракт не меняется: имена команд/инструментов, схемы MCP, формат ответов и текст ошибок сохраняются.
2. Внутренний API добавляется:
`control::ToolCatalog`, `control::UseCaseId`, `control::ContextFactory`, `control::Executor`.
3. `main.rs` и `mcp/mod.rs` переходят на вызов `control` API вместо собственных `match`-оркестраторов.
4. `AnalysisContext`/`Analyzer` публично не меняются по поведению; используется существующий контракт, включая `git_scope`.
5. Семантический индекс расширяется внутренним типом символа `branch`:
`symbol_type = "branch"`, `symbol_name = "<function>::<branch_kind>:<start>-<end>"`, `signature = "<function_signature> [branch:<kind>]"`.
6. Формат выдачи `semantic_search` не ломается: используются существующие поля (`symbol_name`, `symbol_type`, `signature`, `start_line`, `end_line`), но теперь в выдаче легально присутствуют `branch`-результаты.

## Implementation steps (decision-complete)
1. Создать `src/control/mod.rs` и `src/control/types.rs` с `UseCaseId`, `UseCaseInput`, `UseCaseOutput`, `ToolSpec`.
2. Перенести в `control::context_factory` все path/git/context policy из CLI+MCP:
`resolve_requested_path`, `discover_git_root`, `rebase_files_to_git_root`, `build_context`-эквивалент.
3. Сформировать единый каталог инструментов в `control::catalog`:
одна запись = analyzer/use-case + MCP schema + git requirement + CLI binding.
4. Реализовать `control::executor::execute_use_case(...)`:
`AnalyzeSingle`, `AnalyzeDiff`, `SemanticSearch`, `SemanticSearchHyde`, `BatchAll`, `BatchReport`.
5. В `main.rs` заменить orchestration-блоки на делегирование в `control`:
`dispatch_analyzer`, `run_analyzer_with_instance`, `run_search`, `Command::All`, `run_report`.
6. В `mcp/mod.rs` заменить:
`handle_tools_list` на генерацию из `ToolCatalog`,
`is_git_dependent_tool`/`handle_tool_call` на lookup + `execute_use_case`.
7. Свести `handle_semantic_search` и `handle_semantic_search_hyde` в один use-case executor с режимом `SearchMode::{Query,Hyde}`; различается только вход.
8. Оставить transport formatting на местах:
CLI форматтер как сейчас, MCP `content[].text` wrapper как сейчас.
9. Сохранить текущие тексты ошибок 1:1 (path policy, git not found, missing params), чтобы избежать регрессий в агентах.
10. Расширить `semantic::chunking`:
поверх существующих function-chunk'ов извлекать AST control-flow ветви внутри тела функции (`if/for/while/try/...`) как отдельные `Chunk` с `symbol_type="branch"`.
11. Расширить `semantic::chunking::format_chunk_text`:
добавить явный marker `[branch]` в enriched text для branch-символов.
12. Синхронизировать `semantic::sync`:
назначение complexity выполнять по containment-диапазону функции (а не только по имени), чтобы branch-символы наследовали complexity родительской функции.
13. `bdd_coverage` не менять по логике matching:
он остается на сопоставлении Gherkin step -> Python decorator pattern и не зависит от branch-символов semantic index.

7. Parity: одинаковый semantic результат для эквивалентного запроса через CLI/MCP (с учетом wrapper-формата MCP).
8. Regression: не-git путь для git tools дает ту же fail-fast ошибку с подсказкой.
9. Semantic chunking: Python функция с `if` создает минимум один `branch`-символ с корректным `start_line/end_line` и `signature [branch:...]`.
10. Semantic sync: `branch`-символ получает `cyclomatic/cognitive` от enclosing function.
11. Semantic search: запрос по токенам из AST-ветви возвращает результат с `symbol_type="branch"`.
12. BDD regression: `bdd_coverage` output по existing fixtures не меняется по структуре и правилам `Implemented/Missing/Ambiguous`.

## Assumptions and defaults
1. Централизация делается по use-case ответственности, а не по read/write state.
2. Логика анализаторов (`src/analyzers/*`) не переносится и не меняется.
3. Поведение и output contracts остаются неизменными; меняется только место orchestration-кода.
4. Scope включает CLI+MCP+batch orchestration; не включает глубокую переработку parser и других analyzer internals вне явно оговоренного semantic branch-indexing.
5. Уточнение scope: parser API не ломается, но semantic internals целенаправленно расширяются branch-индексацией внутри функций.
6. `bdd_coverage` продолжает работать независимо от semantic cache; AST-ветви не добавляются в его matching-модель, если не появится отдельное продуктовое требование.
